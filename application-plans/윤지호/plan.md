## 1. 대상 업무

### 1.1 핵심 업무

- TV **Home 화면** 및 연관 **네비게이션·위젯·상태 표시** UI (C# + Tizen UI Framework)
- Visual Studio 기반 솔루션의 **기능 추가, 버그 수정, 레거시 정리**
- 기기·플랫폼별 **동작 차이·성능·포커스/리모컨 입력** 이슈 대응

### 1.2 Magic Square 회고와의 연결 (무엇을 가져올지)

교육 프로젝트에서 **현업에 이식 가능한 원칙**만 추립니다.

| 회고에서 Keep/Learn | Home UI에의 재해석 |
|---------------------|-------------------|
| 문제를 「기능 나열」이 아니라 **판정 규칙·불변식**으로 정의 (Report/01) | 화면별 **진입 조건, 포커스 규칙, 데이터 표시 조건**을 짧은 체크리스트·AC로 먼저 적기 |
| **Dual-Track** — Boundary(형태) vs Domain(로직) 분리 | **UI/View 계층**(마크업·바인딩·이벤트) vs **상태·비즈니스 로직**(ViewModel/Service 등) 작업을 AI 요청 시 분리 |
| RED→GREEN→REFACTOR, 실패를 **defect_list**로 문서화 | 기기 테스트 전에 **재현 절차·기대/실제**를 Markdown/이슈에 고정 |
| **Golden Master**로 회귀 방지 | 자동화 어려운 UI는 **스크린샷·동작 시나리오 baseline** 수동 체크리스트로 대체 |
| REFACTOR 전 **계약·포트** 정리 (ECB, `application_contracts`) | 모듈 간 **인터페이스·이벤트 계약**을 먼저 적고, AI 리팩터 범위를 그 경계 안으로 제한 |
| PyQt는 cov 낮고 **수동 스모크** (회고 Problem→Try) | Tizen UI 전체와 **로컬 검증 가능한 C# 로직**의 검증 기준을 **의도적으로 분리** |

### 1.3 AI를 **당장 넓히지 않을** 영역 (현실적 한계)

- 실기기 **풀 빌드·설치·UI 시각 검증**을 AI가 대신할 수 없음 → 1·2차 목표에 포함하지 않음
- Tizen UI Framework **전체 화면을 AI가 한 번에 생성**하는 방식은 리스크 큼 → 보조·분석·부분 수정 위주 유지

## 3. 구체적 활용 방안

### 3.1 1차 — 빌드·UI 테스트 없이도 하는 일 (지금 환경에 맞음)

| 활용 | Cursor / AI 활용 방법 | Magic Square에서 가져온 점 |
|------|------------------------|---------------------------|
| **문제 분석** | 스택 트레이스, 로그, 관련 C# 파일만 @멘션해 **원인 가설·수정 후보** 나열 | defect_list처럼 **가설 → 검증 방법**을 대화에 남김 |
| **소규모 구현** | 기존 패턴이 있는 파일에 **메서드·핸들러 추가** (전체 화면 신규 생성 X) | AC-FR처럼 **「이 조건이면 이렇게 동작」**을 프롬프트에 명시 |
| **국소 리팩터** | 한 클래스·한 화면 파일 내 **이름 정리, 중복 제거, early return** | REFACTOR 전 **「바꾸지 않을 공개 API/이벤트」** 선언 (Report/15 체크리스트 유사) |
| **작업 전 문서** | 세션마다 5~10줄 **「오늘 목표 / 판정 규칙 / 기기 확인 항목」** | Report/Prompt Export 습관 — 현업은 `docs/worklog/YYYY-MM-DD-home.md` 등 경량화 |
| **코드 리뷰 보조** | PR diff 붙여 **ECB 위반·순환 참조·Tizen UI 스레드 이슈** 질문 | Report/13 PR 리뷰, Control→Boundary 역의존 제거 사례 |

**1차 프롬프트 예시 (Home UI):**

```text
TV Home UI, C#, Tizen UI Framework.
수정 범위: {파일명}만. public 이벤트·XAML/마크업 시그니처는 변경 금지.
판정 규칙: (1) 리모컨 Down 시 포커스는 그리드 내에서만 이동 (2) 백키 시 상위로 복귀.
빌드·실기기 검증은 내가 함. 코드 제안과 회귀 체크리스트만 줘.
```

### 3.2 2차 — 「Track A / Track B」 분리 (회고 Dual-Track 응용)

```text
[Track A — UI / Tizen / Framework]
  · 시각·포커스·애니메이션·실기기 동작
  · 검증: 수동 시나리오 + (가능 시) 스크린샷 baseline

[Track B — C# 로직 / 상태 / 데이터 변환]
  · 표시 조건, 필터, 매핑, 유효성 검사
  · 검증: 로컬 단위 테스트 또는 정적 분석 (도입 가능한 범위만)
```

| Track | AI 역할 | 사람이 반드시 할 일 |
|-------|---------|---------------------|
| A | 레이아웃·이벤트 연결 **설명·diff 제안**, 회귀 **체크리스트** 생성 | VS 빌드 → Tizen 배포 → 리모컨 시나리오 확인 |
| B | 테스트 가능한 순수 함수 추출, **테스트 코드 초안** | 테스트 러너·빌드 설정이 팀 표준에 맞는지 확인 |

Magic Square의 **「PyQt cov 0% → 수동 스모크」**와 동일하게, **Track A는 커버리지 숫자 대신 시나리오 문서**로 관리한다.

### 3.3 3차 — 팀·도구 (여유 시)

- **Cursor Rules**: Tizen 네이밍, 금지 API, Home UI 포커스 규칙을 `.cursor/rules`에 요약 (교육 Report/03~04 Rule/Prompt)
- **Golden Master 대체**: 주요 Home 상태(최초 진입, 앱 전환 후 복귀, 오류 배너 등) **「GM-TC-Home-01」** 형식의 수동 시나리오 표 — 회고 Report/14
- **REFACTOR 계획서**: 대규모 구조 변경 전 1페이지 **체크리스트(A~E)** (Report/15~16) — AI에게 범위·금지 사항 전달

### 3.4 Visual Studio · 빌드 환경이 어려울 때의 운영 원칙

1. AI에게 **「전체 솔루션 빌드 성공까지 맞춰줘」**보다 **「이 파일만 컴파일 관점에서 문제 없는지」** 요청
2. 변경을 **작은 PR/커밋**으로 쪼개 기기 검증 부담 감소
3. AI 출력은 **항상 diff 검토** — Tizen·UI 스레드·리소스 dispose는 사람이 최종 확인
4. 교육에서처럼 **실패를 숨기지 않기** — 기기에서 안 되면 defect 항목(재현·버전·캡처)을 이슈에 남기고 다음 AI 세션에 @링크

## 4. 기대 효과·지표

| 항목 | 기대 효과 | 측정 방법(가능한 경우) |
|------|-----------|------------------------|
| **분석·수정 리드타임** | 로그·코드 읽기 시간 단축, 수정 후보 좁히기 | 이슈당 **분석에 쓴 시간** (주관 + 주 1회 메모) |
| **회귀 버그** | 리팩터·기능 추가 후 Home 핵심 시나리오 깨짐 감소 | 1차 도입 후 **Track A 수동 체크리스트** 이행 여부 |
| **리팩터 안전성** | 「건드리기 무서운」 모듈을 **경계 정리 후** 국소 변경 | 2차에서 Track B 테스트 도입 시 **해당 모듈 결함 재발 건수** |
| **문서·추적성** | Magic Square Report처럼 **왜 이 변경을 했는지** 남음 | worklog·PR 설명에 **판정 규칙/AC** 링크 비율 |
| **AI 의존도** | 맹목 적용 감소, 검증 책임은 개발자 | AI 제안 중 **기기 검증 전 merge 비율 0%** (팀 규칙) |

*TV UI는 pytest 101 passed 같은 단일 지표가 어렵기 때문에, **「자동 테스트 수」보다 「시나리오·규칙 문서화 + 수동 GM 이행」**을 1차 KPI로 둔다.*

## 5. 리스크·전제 조건

- **보안·컴플라이언스**
  - 고객·미공개 UI·내부 API 키·실제 사용자 데이터는 Cursor에 붙이지 않음
  - 필요 시 사내 허용 모델·오프라인 정책 준수

- **사내 정책·도구 제약**
  - Visual Studio + Tizen SDK **공식 빌드 파이프라인**이 AI 제안과 다를 수 있음 → AI는 **코드·설계 보조**, 빌드·서명·배포는 기존 절차
  - UI 자동화 도구 부재 시 **Track A는 영구적으로 수동 검증** 전제

- **반드시 사람이 검수할 영역**
  - 실기기 **포커스·리모컨·성능·메모리**
  - Tizen **라이프사이클·권한·스토어/펌웨어 연동**
  - Home UI **브랜드·접근성·다국어** 최종 표시
  - AI가 제안한 **대규모 파일 이동·네임스페이스 변경** (회귀 범위 큼)

- **기대 관리**
  - Magic Square는 **PC·pytest 친화 환경**; Home UI는 **동일한 테스트 밀도를 목표로 하지 않음**
  - 1차 목표는 「AI로 앱 전체 자동 개발」이 아니라 **「분석·소규모 변경·리팩터의 품질·추적성 향상」**
