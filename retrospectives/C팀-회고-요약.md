## 1. 공통적으로 드러난 내용

여러 명이 **같은 키워드·같은 방향**으로 언급한 주제입니다.

### 1.1 방법론·프로세스

| 주제 | 공통 인식 |
|------|-----------|
| **TDD 사이클** | RED → GREEN → REFACTOR를 교육의 중심으로 경험. 「테스트와 구현을 섞지 말 것」이 반복적으로 등장 |
| **문제 정의** | 「기능 만들기」보다 **요구·제약·판정 규칙**을 먼저 쓰는 접근이 유익 (PRD, Mom Test, 5 Whys 등 표현은 다름) |
| **단계·범위 나누기** | AI에게 한 번에 많이 시키지 말고 **「지금은 테스트만 / 코드만」**, **「이 파일만」**처럼 범위를 좁히는 것이 안전 |
| **문서·기록** | Report, Prompt/Transcript, PRD 등 **맥락을 파일로 남기면** 다음 세션·리뷰·이어하기에 유리 |

### 1.2 Cursor·AI 활용

| 주제 | 공통 인식 |
|------|-----------|
| **Rules** | 프로젝트 규칙을 미리 두면 AI 출력이 **팀 기준에 가깝게** 맞춰짐 |
| **맥락 첨부** | `@`로 README·문서·코드를 붙이면 설명 부담이 줄어듦 |
| **생산성 vs 검증** | AI로 속도는 올릴 수 있으나, **검증·설계·리뷰 역량**이 함께 필요하다는 인식 (이민준, 이승환, 이영실 등) |
| **출력 검증** | AI 제안을 그대로 믿기보다 **테스트·AC·동료 리뷰**로 확인해야 함 |

### 1.3 협업·리뷰

| 주제 | 공통 인식 |
|------|-----------|
| **코드 리뷰** | 단순 승인이 아니라 **기준( AC, 계약, 아키텍처 )을 맞추는 과정**으로 이해하는 면목 |
| **팀·페어** | AI 결과 공유, 역할 분담(문서/테스트/코드), 리뷰 포인트 학습 등 **협업 가치** 언급 |

### 1.4 막혔던 점 (공통 패턴)

- **RED/GREEN 경계** — 테스트만 할 단계와 구현 단계가 섞이면 혼란
- **프롬프트·범위** — AI가 범위 밖을 수정하거나, 출력이 길어 **의도와 다른 결과**
- **학습 곡선** — 2일 짧은 과정, 따라가기 바쁘거나 이론·실무 간격을 느낌

## 2. 사람마다 다르게 강조한 내용

같은 교육을 들었지만 **초점·깊이·표현**이 다른 부분입니다.

| 이름 | 강조한 축 | 대표 키워드 |
|------|-----------|-------------|
| **윤지호** | **기술·프로세스 심화** | Dual-Track, ECB, Golden Master, defect_list, pytest-cov gate, PR/브랜치, Report 01~16 단위 추적 |
| **이수진** | **팀 협업·거버넌스** | 1커밋=1 RED, AC ID, SSOT, GM approve를 리뷰 기준으로, Ask 모드로 설계 선행 |
| **이승환** | **프롬프트·운영 단순화** | Rules + `@` + 단계별 지시, 대화 길어질 때 Report로 재시작, **Cline** 등 현업 도구 연계 언급(계획서) |
| **이민준** | **Discovery / Delivery** | Dual Track을 **문서와 개발 병행** 관점에서, PRD 구조화, Prompt 재사용 자산화 관심 |
| **이영실** | **거시 방법론** | Concept to Code, **traceability**, **shift left** — 구현 디테일보다 프로세스·품질 관점 |
| **이재호** | **Legacy·실무 전환** | 기존 에이전트 사용 vs 교육 패턴, **레거시에 TDD 적용** 막막함 → 사례 실습으로 완화 |

### 2.1 깊이 차이

- **상세 기술 회고**: 윤지호, 이수진 (Magic Square 실습을 AC·테스트·아키텍처 단위로 풀어 씀)
- **원칙·운영 중심**: 이승환, 이민준 (짧지만 실천 가능한 습관 위주)
- **개념·태도 중심**: 이영실, 이재호 (방법론 이름·느낌·현업 적용 고민 위주)

### 2.2 「팀 활동」 서술 차이

| 이름 | 팀/페어에서 본 것 |
|------|-------------------|
| 윤지호 | 1인+AI 페어, PR 리뷰가 REFACTOR 입력, Report/Prompt가 「최소 협업 문서」 |
| 이수진 | AC ID·GM·RED/GREEN을 **리뷰 합의 언어**로 사용 |
| 이승환 | 역할 나누기, **계획 먼저·구현 나중** |
| 이민준 | AI 결과 공유·리뷰로 **검증의 중요성** |
| 이영실 | 코드 리뷰로 **다양한 리뷰 포인트** 학습 |
| 이재호 | 직접보며 **자동화·기계화된 절차가 왜 필요한지** 체감 |

## 3. 색다르게 느낀 점 · 팀 내 특이 인사이트

개인만의 각도이거나, 다른 멤버 회고에는 거의 없는 표현입니다.

### 3.1 윤지호

- **실패를 자산화**: RED 24 fail → `defect_list.md` 5건 근본 결함 → CLOSE까지 **결함 추적 워크플로**
- **커버리지 3단계**: PyQt/UI는 cov 0%에 가깝다는 현실을 **A/B/C 게이트로 분리**해 오해 방지 — *TV·UI 개발자에게 특히 와닿을 수 있는 사례*
- **REFACTOR 안전망**: GM 18건 + approve, ECB Port/Adapter로 **101 passed 유지**한 구체 수치
- **AI 지시 패턴**: 「RED만 / GREEN만」처럼 **범위를 반복해서 좁히는** 사용자 지시가 transcript에 남는다는 메타 인사이트

### 3.2 이수진

- **The Mom Test** — 「만들고 싶은 기능」→「관찰된 상황」 (다른 팀원은 PRD·5 Whys 등 다른 이름)
- **1커밋 = 1 RED** — 커밋 단위 습관을 명시적으로 팀 규칙 후보로 제시
- **Ask 모드로 설계 선행** — Agent로 코드 생성 **전에** PRD·AC 정리
- **리뷰 문화**: 「LGTM」보다 **PRD·AC·In/Out-of-Scope**를 적는 리뷰
- **다음 주제**: Phase 0 Gate CI, Domain Mock 금지 등 **팀 자동화·거버넌스** 목록이 가장 구체적

### 3.3 이승환

- **대화 맥락 유실 대응**: 긴 세션 후 **요약 Report + `@README` 재시작** — 실무 프롬프트 운영 팁
- **한 줄 요약의 격언 형태**: 「규칙 + 문서 첨부 + 단계 나눠 말하기 → **테스트로 꼭 확인**」
- 현업 계획(별도 문서)에서 **Cline** 등 Cursor 외 도구 시범 — 팀 내 유일한 도구 다양성

### 3.4 이민준

- **Dual Track = Discovery / Delivery** — Track A/B 마방진 용어가 아닌 **제품 발견·전달** 프레임
- **Prompt를 재사용 가능한 자산**으로 만드는 것에 관심 — 장기 운영 관점
- 회고는 짧지만 **「생산성 ↑, 검증·설계 역량 필수」** 균형을 분명히 짚음

### 3.5 이영실

- **Concept to Code · traceability · shift left** — 유일하게 **추적성·좌측 이동**을 1번 섹션 핵심으로 둠
- AI에 대한 **양면 감정**: 「든든한 조력자」 vs 「출력 방대·시간 소요·원치 않는 결과」
- **beautiful code** — 정성적·동기 부여형 한 줄 요약 (다른 멤버는 프로세스·수치 중심)

### 3.6 이재호

- **Legacy + TDD 괴리** — 「이론과 실무의 괴리」를 솔직히 쓰고, **레거시 리팩터링 방법론**을 다음 학습 주제로 명시
- **Agent/Skill** — 교육 중 실사용은 제한적이었으나 **복귀 후 활용 기대**가 큼
- **기계화된 기능의 이유** — TDD·GM·Rules를 「왜 필요한지」 체감했다는 **메타 학습** 표현
- 톤: 「정신없이 따라함」「더 공부해야겠다」 — **겸손·추가 학습 의지**가 두드러짐

## 5. 팀 차원에서 읽을 수 있는 시사점

1. **공통 기반은 「규칙 + 단계 + 검증」** — Rules, TDD 단계, 테스트/리뷰 확인은 전원이 공감하는 최소 세트.
2. **심화 축은 둘로 갈림** — (A) Magic Square 기반 **엔지니어링 디테일**(윤지호·이수진) vs (B) **운영·방법론·Legacy**(이승환·이민준·이영실·이재호).
3. **회고 완성도 ≠ plan 완성도** — 회고는 6명 모두 작성, 현업 적용 계획(`plan.md`)은 일부만 상세 (별도 [README 멤버 링크](../README.md) 참고).
4. **다음 모임에서 나눌 만한 주제**
   - 이수진·윤지호: AC ID, GM approve, CI gate를 **팀 최소 규칙**으로 할지
   - 이재호·이영실: **Legacy / shift left**를 현업에 어떻게 줄일지
   - 이승환·이민준: **공통 프롬프트·Report 템플릿** 공유
