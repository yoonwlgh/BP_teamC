## 1. 교육에서 가장 도움이 된 내용

- **TDD (RED → GREEN → REFACTOR)**  
  2일차 UI·Logic 동시 진행으로 TDD 사이클을 몸에 익혔다. **1커밋 = 1 RED** 원칙도 같이 배워서, 커밋 하나에 실패 테스트 하나씩만 묶는 습관이 생겼다.

- **The Mom Test**  
  1일차에 문제를 “만들고 싶은 기능”이 아니라 “관찰된 상황”으로 쓰는 법을 배웠다. MagicSquare도 “마방진 만들기”가 아니라 “4×4 격자 제약을 어떻게 판정·고정할 것인가”로 정의하는 데 도움이 됐다.

- **Dual-Track 병렬 설계**  
  Track A(Boundary/UI)와 Track B(Domain/Logic)를 나눠 RED를 깔 수 있었다. 한쪽을 막아도 다른 트랙은 계속 진행할 수 있는 구조가 좋았다.

- **ECB 책임 분리**  
  Boundary → Control → Entity 의존 방향을 Rules로 고정해 두니, AI가 생성하는 코드도 계층을 크게 벗어나지 않았다.

- **Golden Master**  
  기대 출력을 미리 고정해 두고 회귀 기준으로 쓰는 개념. TD-01/TD-02 같은 테스트 데이터와 연결해 이해했다.

- **Cursor Ask 모드**  
  Agent로 코드를 바로 만들기 전에, Ask 모드로 PRD·AC·설계를 먼저 질문·정리하는 데 썼다.

## 2. 처음 써 본 기능·워크플로

| 기능/워크플로 | 간단한 사용 경험 |
|---------------|------------------|
| **Dual-Track TDD** | UI RED와 Logic RED를 동시에, 이후 GREEN·REFACTOR로 나눠 진행 |
| **1커밋 = 1 RED** | FR-01 RED 테스트 추가 → GREEN 구현 → 스켈레톤 추가를 커밋 단위로 분리 |
| **ECB + `.cursorrules`** | Boundary/Control/Entity 역할을 Rules에 적어 Agent 출력을 맞춤 |
| **AC ID 추적** | `AC-FR01-01`, `TC-SIZE-001` 등 ID로 PRD–테스트–코드를 연결 |
| **mock/spy 격리 테스트** | Boundary 실패 시 `Control.resolve` 미호출(`AC-FR01-05`) 검증 |
| **RED 스켈레톤** | GREEN 전 `pytest.fail("RED: …")`로 구조만 먼저 깔기 |
| **Transcript Export** | 세션 기록을 `Prompting/`에 남겨 팀과 맥락 공유 |

## 3. 막혔던 점과 해결 방법

| 어려움 | 어떻게 해결했는지 |
|--------|-------------------|
| **RED ↔ GREEN 경계 혼용** | FR-01 Full RED/GREEN과 Dual-Track 스켈레톤 RED를 브랜치·Report로 단계 분리 |
| **프롬프트 엔지니어링 부족** | `[P] QA`, `[C] Python`, `[T] 테스트 계획서`처럼 역할·맥락·과제를 나눠 적기 |
| **AI 제안 검증 능력 미흡** | PRD·AC·오류 계약(`INVALID_SIZE`)을 SSOT로 두고 Agent 출력을 하나씩 대조 |
| **커버리지 목표 미달** | Boundary 85% / Domain 95% 목표를 `test_plan.md`에 적어 두고, 아직 GREEN 범위만 측정 |
| **ECB 레이어 책임 혼재** | “Domain resolver” 같은 모호한 용어를 `Control.resolve`로 고정해 테스트·문서에 통일 |
| **PRD 파일 미저장** | Report·transcript에서 FR-01 계약을 역추적해 작업 기준 확정 |

## 4. 팀 활동·페어 작업에서 배운 점

- **코드 리뷰를 “통과/반려”가 아니라 합의 과정으로**  
  PR·커밋 리뷰에서 AC ID, In/Out-of-Scope, RED/GREEN 단계를 같이 확인했다. “LGTM”만 남기기보다 **무엇이 PRD와 맞고, 무엇을 고치면 좋은지** 적는 게 협업에 더 도움이 된다는 걸 배웠다.

- **Golden Master approve를 팀 기준으로 맞추기**  
  TD-01/TD-02 기대 출력·오류 코드(`INVALID_SIZE` 등)를 리뷰 때 SSOT로 삼아, “이 값이 맞는지”부터 합의하고 구현 논의로 넘어갔다.

- **Dual-Track 병렬 설계의 협업 이점**  
  Track A(입력 검증)와 Track B(도메인 로직)를 나눠 두니, 리뷰도 슬라이스 단위로 나눠 볼 수 있었다.

- **AC ID로 같은 언어 쓰기**  
  `AC-FR01-01`, `AC-FR01-05`처럼 ID를 공통으로 쓰니, 리뷰 코멘트가 “이 줄 왜 있어?”가 아니라 “이 AC를 검증하는 테스트”로 연결됐다.
