## 1. 교육에서 가장 도움이 된 내용

- 단순히 Agent에게 "기능 만들어줘"라고 시키는 방식으로는 10GB+ Legacy 초음파 S/W에 AI를 적용하기 어렵다는 것을 다시 확인했습니다. 대신 **AC ID · ECB Layer · Phase(RED/GREEN) · Golden Master** 같은 Guardrail을 먼저 두면, AI가 작업할 **범위가 좁아지고 검증 가능**해진다는 점이 큰 수확이었던 것 같습니다.
- **Dual-Track**(Platform/Boundary vs Product/Entity·Control) 병렬 설계, **1커밋 = 1 RED**, **Golden Master로 회귀 보호**, **Ask(분석) → Agent(구현)** 분업 — 이 네 가지가 "Legacy에 AI를 어떻게 붙이나"에 대한 실질적인 답이었습니다.
- 막연했던 상황에서 무엇이 부족한지(Dual-Track, ECB, GM, RED↔GREEN 혼용, 프롬프트·검증 역량 등) 대략적으로나마 알 수 있게 된 것 같습니다.
- MagicSquare PoC(Report/16·17)를 보면서, **Phase 0 Gate**(커버리지·GM·Control 테스트)를 통과한 뒤에야 REFACTOR/기능 추가로 들어가는 순서가 Legacy에는 어떻게 적용할지 고민이 참 많이 되고 있습니다.

## 2. 처음 써 본 기능·워크플로

| 기능/워크플로 | 간단한 사용 경험 |
|---------------|------------------|
| **Agent** | RED-only / GREEN-only로 좁은 스코프(파일 몇 개, AC 1건)에 사용했습니다. 테스트와 구현을 한 번에 시키면 Phase가 섞이므로, **한 턴에 RED 또는 GREEN 중 하나만** 지시하는 것이 중요하다는 것을 체감했습니다. |
| **Ask 모드** | 코드 변경 전 영향 범위·ECB 위반·AC traceability를 분석할 때 유용했습니다. Legacy처럼 규모가 큰 코드베이스에서는 Agent보다 Ask를 먼저 쓰는 것이 안전합니다. |
| **Skill / Rule** | `.cursor/rules`로 ECB·Phase·Mock 금지 규칙을 고정하면, 매번 같은 프롬프트를 반복하지 않아도 됩니다. 현업 복귀 후 팀 SSOT로 만들 가치가 있다고 생각합니다. |
| **Dual-Track TDD** | Track A(Boundary)와 Track B(Entity/Control)를 분리해서 RED→GREEN을 진행했습니다. 통합은 Golden Master에서만 확인하는 흐름을 처음 따라 해 보았습니다. |
| **Golden Master** | 기존 동작 출력을 baseline으로 고정하고, REFACTOR/변경 후 diff로 회귀를 판정합니다. Legacy에 테스트가 부족할 때 "안전망" 역할을 한다는 개념을 실습으로 이해했습니다. |

## 3. 막혔던 점과 해결 방법

| 어려움 | 어떻게 해결했는지 |
|--------|-------------------|
| **이론과 실무의 괴리** — TDD·ECB는 알지만 10GB Legacy에 어디서부터 시작할지 막막 | MagicSquare PoC로 **축소판**을 직접 따라 하면서, "전체"가 아니라 **Pilot 모듈 1개 + AC 1건**부터 Gate를 거는 순서를 익혔습니다. |
| **RED↔GREEN 경계 혼용** — Agent가 테스트와 구현을 동시에 제안 | PR/커밋 단위로 Phase를 분리하고, RED 커밋에는 `src/` 변경 금지 원칙을 적용했습니다. 프롬프트에 **Phase: RED only**를 명시했습니다. |
| **ECB 레이어 혼재** — ViewModel·Control·Entity 책임이 섞이기 쉬움 | Boundary / Control / Entity 역할 표를 기준으로 Ask에서 "어느 레이어인지" 먼저 판별했습니다. **도메인 Mock 금지**, Port만 mock합니다. |
| **AI 제안 검증** — diff가 맞는지 판단하기 어려움 | GM diff + AC ID traceability + 커버리지 gate로 **기계적 검증**을 먼저 통과시키고, Clinical·성능 등은 사람 검수 영역으로 분리했습니다. |
| **프롬프트 작성** — 무엇을 넣어야 AI가 범위를 벗어나지 않는지 불명확 | Agent 세션 시작 **4줄**(AC ID · Phase · ECB Layer · In-scope files) 템플릿을 사용했습니다. Out of scope도 명시했습니다. |

## 4. 팀 활동·페어 작업에서 배운 점

- 직접 따라 하면서, **기계화된 기능**(Phase Gate, CI, GM approve, Traceability 표, `.cursor/rules`)이 형식적인 절차가 아니라 **AI·사람 모두의 작업 범위를 제한하는 Guardrail**이라는 것을 이해했습니다.
- 페어로 RED→GREEN→GM 흐름을 밟으면서, 혼자 할 때보다 **Phase 분리·ECB 위반**을 서로 잡아주는 것이 훨씬 수월했습니다. 복귀 후에도 주 1회 AI diff 리뷰 rotation 같은 형태가 필요하겠다는 생각이 들었습니다.
- Platform / Product 이원 구조는 우리 초음파 S/W와 닮아 있어서, MagicSquare의 Dual-Track을 현업에 **추상적으로 나마 적용해 볼 수 있겠다** 생각됩니다.
